# Account deletion

Account deletion is available only from Profile → Privacy & safety and requires a warning plus a short-lived, cryptographically random final-confirmation nonce. Cancel, Back, or another profile destination clears the persisted confirmation state, so stale cards cannot authorize deletion.

Cleanup is coordinated by `src/services/account-deletion.js`. A durable `AccountDeletion` operation claims execution, records progress, and permits idempotent retry. Open owned discussions are closed without ownership transfer; membership, recent messages, reports, invitations, mutes, taste indexes, paid AI drafts, pending pre-onboarding inline-list selections, legacy People entitlements, boost deliveries, saved-profile references, and personal analytics metadata are removed. The User document is removed last.

Star transactions, qualified referral facts, and boost audit rows are retained only for reconciliation and anti-abuse. Their numeric Telegram identity is replaced by a unique random negative tombstone, never a shared sentinel. Referral-claim invitee identities use per-claim negative tombstones when repeated account lifecycles would otherwise collide with the claim's unique index. Retained ledger idempotency keys are namespaced with their immutable transaction IDs during anonymization, freeing the original keys so a genuinely recreated account can earn one-time rewards again. Referral links are expired and assigned to the tombstone; their already-opaque public codes remain unchanged so multiple links can be anonymized without violating the unique-code index. A keyed identity fingerprint in the deletion operation permits recreation checks without retaining the raw Telegram ID. Deployments must provide `ACCOUNT_DELETION_SECRET` (or, for compatibility, `BOT_TOKEN`) consistently for the lifetime of the service.

Deletion forfeits the wallet balance. Ordinary messages and callbacks cannot recreate a missing account. `/start` or the localized `🌱 Start again` action may create it; either restart route is authorized by a durable, one-time `restartedAt` claim on the completed deletion record. On that first restart, any stray User document left by an interrupted or older deployment is removed before a genuinely fresh User is created. The reply keyboard is consumed when language selection opens, normal onboarding runs, and a new public-profile code is assigned. Later restart-label messages cannot erase an established account. A recreated account may be deleted again; beginning that later deletion safely resets the completed operation for a new cleanup cycle while retaining its audit tombstone. If an older deployment recreated the User without recording `restartedAt`, the presence of that active User also resets the deletion operation so the next confirmed deletion actually removes it. Old profile and invitation links do not resolve.

Notification delivery is best effort. Cleanup failures after work begins remain resumable by opening Profile → Privacy & safety and starting Delete account again; the UI never reports success until required cleanup completes. Telegram messages already delivered to another chat are outside Muze's database and can remain visible.
